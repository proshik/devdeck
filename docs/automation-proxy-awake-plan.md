# Прокси и «Без сна» в `DevDeck automation`

## Запрос

Добавить в CLI `DevDeck automation …` управление прокси (выбор LAN/удалённого прокси,
проверка, раздача этого Mac) и режимом «Без сна» (работа с закрытой крышкой). Поведение
согласовано с пользователем 26 ноября 2026 года.

## Поведение (контракт)

```sh
# Прокси, клиентская сторона
automation proxy list                     # найденные в LAN и удалённые (VDS): имя, тип lan|remote, живой ли, нужна ли auth
automation proxy status                   # что выбрано, его состояние; состояние раздачи и число клиентов
automation proxy use <name|UUID>          # LAN-прокси или удалённый; для удалённого поднимаются ssh-туннель и мост
automation proxy use none                 # снять выбор; туннель удалённого гасится
automation proxy check                    # проверить активный прокси, показать exit IP

# Прокси, раздача этого Mac
automation proxy share on|off|status
automation proxy share set [--port N] [--engine builtIn|gost] [--service-name S] [--auth on|off] [--username U]

# Без сна
automation awake on [--for 30m|2h|0]      # 0 = бессрочно; верхний предел тот же, что в UI (2 ч)
automation awake off
automation awake status                   # вкл/выкл, сколько осталось
```

Правила:

- В Settings → Automation два новых переключателя: «Прокси» и «Без сна», по умолчанию
  выключены (`settings.automationProxyEnabled`, `settings.automationAwakeEnabled`,
  декодируются с `false`, `schemaVersion` не меняется). Выключен → отказ, код 3. Общий
  переключатель Automation по-прежнему обязателен. Коды выхода — существующие.
- Пароли через CLI не принимаются никак. LAN-прокси требует auth, а сохранённых данных нет →
  `use` отказывает и просит ввести их в UI. `--auth on` без пароля раздачи в Keychain → отказ.
- `share set` при запущенной раздаче перезапускает её, как сохранение в UI.
- Удалённые прокси через CLI не добавляются, не удаляются и не редактируются — только выбор
  и снятие выбора.
- `proxy use` ведёт себя как выбор в UI (выбор LAN-прокси гасит удалённый туннель): вызываются
  те же методы `ProxyManager` (`setActiveProxy`, `setActiveRemoteProxy`, `checkActiveProxy`,
  `setShareEnabled`, `saveShare`), логика не дублируется.
- Действия идут через существующие модели и движок (synthetic daemon commands, супервизия);
  собственного жизненного цикла процессов в автоматизации нет.
- Вывод — блоки строк `key: value` (как у `brightness`/`status`), блоки разделены пустой
  строкой; ключи английские и фиксированные, `message` — на языке DevDeck. Справка
  (`automation help`) и README дополнены, тексты EN и RU.
- Вне контракта: новые экраны, App Intents для новых операций, редактирование команд через CLI.

## Решения

- «Бессрочно» — без таймера, как в UI: выход из DevDeck, 20% заряда на батарее и перегрев
  по-прежнему завершают сессию; справка и README говорят именно так.
- Для `proxy use`/`share` «поднялся» значит «демоны в `daemonRunning`», как в панели; готовность
  ssh-подключения движок не сообщает, маршрут доказывает `proxy check`.
- Изменения прокси при неспасаемом `config.json` (не декодируется или запись упала) — отказ, а не
  успех со старыми данными.
- `--for`: `0` (бессрочно), целое число секунд, `Ns`, `Nm`, `Nh` и их сочетания (`1h30m`);
  1 с…2 ч. Без `--for` — длительность, выбранная в UI (по умолчанию 2 ч). CLI не меняет
  выбор длительности в UI: длительность передаётся в `AwakeModel.start` параметром.
- «Сколько осталось»: `AwakeModel` запоминает длительность запущенной сессии; отсчёт идёт от
  квитанции помощника (`/var/run/devdeck-awake.ready`, пишется после `pmset`), за тем же
  пробником, что и остальное.
- CLI не пишет и не удаляет пароли в Keychain: `--auth off` оставляет сохранённый пароль
  раздачи, поэтому последующий `--auth on` снова работает. (UI при сохранении с выключенной
  auth пароль удаляет — CLI это не повторяет, раз пароли через него не проходят.)
- `--auth on` требует и имя пользователя: без него listener был бы открытым при объявленной auth.
- Сохранённые данные LAN-прокси — имя пользователя в конфиге и пароль в Keychain. Модель
  хранит имя только для текущего выбора, поэтому без повторного ввода в UI CLI может выбрать
  auth-прокси, только если он уже выбран (повторный `use` идемпотентен).
- LAN-прокси адресуется точным именем (как в списке), удалённый — именем или UUID. Совпадение
  имён LAN и удалённого — отказ «неоднозначно» со списком. `none` зарезервировано.
- `share on` с движком gost без установленного gost и `share set --engine gost` без gost —
  отказ до изменений.
- Ожидания: удалённый прокси и раздача — до 15 с, проверка — до 15 с, включение «Без сна» —
  до 45 с (пароль администратора), выключение — до 15 с, выключение раздачи — до 10 с.
- Новые поля запроса необязательные, версия протокола остаётся 1.
- Найдено на проверке и по решению пользователя исправлено здесь же: при выборе удалённого прокси,
  когда уже выбран другой удалённый, `ProxyManager.setActiveRemoteProxy` не гасил прежний туннель
  и не перезапускал мост на порты нового (так же было при клике в панели). Теперь прежняя пара
  останавливается, мост перезапускается для нового прокси.

## Известные ограничения (после ревью)

- Ошибка записи исправного `config.json` (не повреждённого — например, диск полон) обнаруживается
  после действия: CLI вернёт код 1, но процессы к этому моменту уже запущены/остановлены. Чтобы
  действовать только после записи, `CommandStore` должен возвращать результат — это правка общего
  кода UI, вне контракта.
- Неудачная запись `proxy-bridge.json` при выборе удалённого прокси даёт код 2 через 15 с вместо 1.
- Существовали до ветки, не менялись: пароль LAN-прокси в аргументах curl у общего пробника;
  `use none` гасит и отдельно запущенные туннели других удалённых прокси; снятие выбора не отменяет
  watchdog упавшего туннеля; остановка не отменяет незавершённую проверку порта.
